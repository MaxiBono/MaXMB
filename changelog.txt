1. Folder Color, Folder Color Pick and Theme Folders
------------------------------------------------------------------------

New: three options in Theme Settings > Text and Color, after Clock Color.

- Folder Color ("On: Make all folders share the same color."), On by default, as Icon Color:
  user.theme.folderColorAll. Off: every folder in its own colors (the system's plain
  folders, a theme's own colors), whatever Folder Color Pick or a PS3 theme's Theme Color
  says.
- Folder Color Pick (no description, as Icon Color Pick): the color of every folder, with
  Icon Color Pick's choices. Original (the default) takes the background's color, as Icon
  Color Pick's Original does.
  - xmb-themes.js _applyFolderColor(): sets --folder-color (the user's choice, or the
    background's color, ICON_AUTO_RGB; white, no tint, with Folder Color Off); called when
    themes apply, on a snapshot restore and from onIconAuto (xmb.js), so Original follows the
    background.
  - styles.css: every folder frame's .ff-tint uses var(--folder-color). The old --folder-tint
    (a PS3 theme's color on its own folders) and .ff-set (an Icon Set's folder in the Icon
    Color) are gone: all folders take Folder Color Pick.
- Theme Folders ("On: The folders of Custom Themes, Icon Sets and PS3 Themes are shown instead
  of the default ones."), Off by default.
  - themes.js setThemeFolders(on); themeIcon(name, folder) gives no theme picture for a folder
    while it's Off, so every folder is the system's, Icon Sets included. On: Icon Set first,
    then the Custom Theme, then the PS3 theme, as for the other icons; a PS3 theme's music /
    video album folder pictures apply too (its "no thumbnail" pictures stay the system's).
  - xmb-themes.js: a PS3 theme's folder pictures are loaded with its other icons (no longer
    left out), so Theme Folders can show them.
  - A Custom Theme's pictures that came from a PS3 theme (Create Custom Theme records them in
    settings.p3tIcons; older Custom Themes: the folder and album pictures a PS3 theme has,
    P3T_FOLDER_PICS) count as the PS3 theme's: never used for the P3T_KEEP pictures.
  - xmb-shared.js itemIcon: folder frames always ask for the folder picture
    (sysUrl(name, true)). Music / Photo folders holding a cover use a plain folder picture
    (music_folder.png / photo_folder.png), a name the system and Icon Sets have but PS3 themes
    don't: when no theme has it, the themes' album picture (icon_music_album_default.png /
    icon_photo_album_default.png) holds the cover, drawn whole.
  - Fitted like the system's folders (xmb-shared.js folderFit): themes draw their folder
    pictures at their own sizes (a PS3 theme's icon_gamedata.png often a 128 x 128 square
    where the system's is 314 x 178; album pictures filling more or less of theirs).
    - opaqueBox(): each picture measured once: its solid part (alpha over 128; with nothing
      solid, as a see-through glass folder, what's seen of it) and everything seen (over 16:
      glows, shadows, faded decoration).
    - The solid part is scaled to fill the system folder's (FF_SYS: the wide Game / Video
      folder, the square Music folder, the Photo folder, measured the same way), centred;
      the folder tint follows it. The icon / cover goes where it sits in the system folder
      (FF_THUMB, as styles.css .ff-thumb), in proportion to the solid part, still whole: the
      folder shows under, beside and over it as the system's does.
    - Sized with the theme's own icons (themeFolderScale): the median visible height of its
      item icons (icon_*, not its folders) against the system's (SYS_ICON_FILL 0.58), between
      0.75 and 1.33 times; fewer than 5 such icons: as the system's.
    - Everything seen in the picture stays inside the frame: a folder with a big decoration
      around it comes out smaller instead of spilling out, and is moved back in where it
      would leave it.
    - Set as inline styles; a picture not loaded yet (or fully transparent) is drawn as it
      is. The measurements go with a theme's pictures, 10 s after it's no longer used
      (forgetFolderFits, called with dropThemeShades).
- Game Data Utility and every other place that isn't a folder keep the themes' pictures.
- All three are saved in Custom Themes (folderColorAll, folderColor, themeFolders); Reset
  Theme Settings puts them back to On, Original and Off.

2. Themes
------------------------------------------------------------------------

- PS3 themes with Theme Color on: xmb-settings.js _tcol(prop) gives the theme's color while
  it's in use, else the user's own. Background Color, Wave Color, Dot Color and Folder Color
  Pick (THEME_COLOR_CTLS) show it as their current value, and their menus have it selected
  ("Theme Color (#HEX)" added at the top when it isn't one of the listed colors). The user's
  own choices are kept underneath and come back when the theme or its Theme Color is turned off.
- Icon Sets and Sound Effect Sets come first: an icon or sound the set has is the set's, then
  the Custom Theme's, then the PS3 theme's. xmb-themes.js _applyThemeSounds: a Sound Set
  without its own Error sound uses its Enter sound for it, before a Custom Theme's Error sound.
- Custom Themes also save the Reactive Icons over Background/Overlay setting, Intro Icon and
  Intro Title (their files copied into the theme's media folder like the other pictures).
- Only what's in use is kept:
  - chroma.js clearLayer: a Background / Overlay video replaced is stopped and lets go of its
    file (pause, src removed, load); ChromaKeyVideo.stop gives the Overlay keyer's WebGL
    context back at once (WEBGL_lose_context).
  - xmb-themes.js _applyThemes: an Icon Set with Transparency off: its solid copies go with the
    theme (they were never let go of); the pictures they were made from are kept while in use.
  - iconshade.js dropThemeShades(live, gone): 10 s after a theme's pictures are let go of, the
    shading made for themes no longer in use is dropped, with the decoded pictures
    (_imgCache / _imgLoaded) and the shading made from them.

3. Icons and Icon Styles
------------------------------------------------------------------------

- playericons.js (new): the Music Player's, Video Player's and Photo Viewer's icons (Control
  Panel buttons, status icons, boxes) are redrawn in the Icon Style in use (Glass (Reactive):
  clear glass; Glossy: the sheen; Flat: one flat color, the marks drawn inside the pictures
  left see-through; Glow / Glow (Pulsating): with the glow; Original styles: as they are);
  the Icon Color is put on afterwards. A MutationObserver on #musicplayer and #mediaview
  redraws pictures as the players draw them (data-psrc / data-psh), cached; xmb.js
  _applyIconStyle calls setPlayerIconStyle(style).
  - Glow: each player icon glows in the color of its own edge as drawn (--pg-c), in the Icon
    Color when that's put on the icons (setPlayerGlowTint).
  - Glow (Pulsating): no CSS animation on the players' icons; pulse() sets the glow's strength
    (0.3 to 1 and back every 3.4 s, --pga, inherited) on the player about 6 times a second
    while it's on screen; nothing runs when it isn't shown, the window is hidden, in low power
    or in a game.
  - The Flat pictures and glow colors made for the players are dropped when another style is
    chosen.
- Reactive Icons over Background/Overlay (Theme Settings > Icons, under Icon Style; "The
  Reactive Icon Styles effects work over Backgrounds and Overlays. This option could be very
  taxing on slower computers."), Off by default, saved as user.theme.reactiveBackdrop.
  - glasslayer.js setBackdrop(on): the glass bends what's behind the icons, in screen order:
    PS3 theme background (#p3tbg), wallpaper (with its Background Display fit), background
    tint, overlay (with its fit and opacity), the wave, and the columns' own backgrounds
    (.bg-layer, a game's background). Off: the wave only.
  - _compose(): put together on the graphics card into a texture at half the wave's size
    (_initCompose, scissor per layer box, blending for opacity), nothing read back. _layerTex /
    _upLayer: a picture copied once (again if it changes); a video's frame only when it has a
    new one (requestVideoFrameCallback), at most 15 times a second, through a copy of at most
    640 x 360; a picture the page may not read is left out instead of spoiling the backdrop.
    _layers() looked at again at most every 0.1 s. The wave is a layer from its own texture,
    copied as it's drawn, so it's there between its frames. _freeBackdrop() lets go of the
    framebuffer, textures and the game background's copy when it's turned off.
  - chroma.js readableFrom(el, src): Background / Overlay pictures and videos from the asset
    address are loaded with crossOrigin "anonymous" (or as before, shown but not bent, when
    that fails); p3tbg.js the same for a PS3 theme's background picture. chroma.js and p3tbg.js
    call window.__onLayerFrame right after they draw.
- Loading icons: the section icon in the middle of the loading icon is always the system's own
  picture (xmb.js _secFlat, sysBase), never a PS3 theme's / Icon Set's.
- Icon shading cache:
  - iconshade.js dropShaded(): the shaded icons dropped (pruneShades, dropOtherStyles,
    dropThemeShades, clearShades) also forget the pictures decoded from them (they stayed in
    _imgCache / _imgLoaded for good: a whole set more with every Icon Style / Color change).
  - xmb-iconstyle.js: the saved shading is loaded once at start as a promise (_xsLoadSaved,
    _xsLoadDone); _applyXmbwShading waits for it and shades from it (the log-in screen's icons
    were shaded again at every start). xmb-themes.js _preshadeTheme waits for it too.
  - Before anyone has signed in, nothing is dropped, pruned or saved (_applyIconStyle,
    _xsScheduleSave): the log-in screen's style and color are only for the moment, and
    dropping the others threw away the saved shading of the user who then signed in (every
    icon shaded again at sign-in when that user had another Icon Style or Icon Color).

5. Menus, scrolling and keys
------------------------------------------------------------------------

- Scrolling in long lists:
  - xmb.js _snapScroll(): the columns where held scrolling may snap: Music, Photo, Video, Game,
    Friends and your own sections ("sec:..."). There, _heldStep (held, one row a step) and
    _glideStep (held, sped up) put the rows in place at once for the rest of the hold once the
    hovered row has fallen further behind its place than one step slides it (_behind: the step
    from the next row's place to the hovered one's plus half a row; _selDrift: its live
    position). Only a held key or direction (window.__inputRepeat) can start it; separate
    presses slide as in v1.1.0.
  - _windowRange: 9 rows above (as in v1.1.0), 14 in those columns.
- Held direction keys (main.js): the arrows and the Left Stick keys repeat on the controller's
  own clock (kbRepTick): the first repeat 380 ms after the press, then one every 130 ms, on
  the display's frames, until the key is let go or the window loses the focus; Windows' own
  repeats of them are left out (its uneven pace made the lists scroll in bursts). In a text
  field the arrows keep Windows' repeat. The keys down are kept (_keysDown): another keydown of
  a key that wasn't let go is its repeat, marked as one or not (some keyboards send a held
  key's repeats as new presses); used for the lists' speed-up, the Music Player (no held-key
  repeats) and Close System.
- Triangle menus and settings option menus:
  - Always the panel with the lighter background and colored stripe (gamemenu.js "bg", with
    "nobg" only changing blur and labels; ui.js SideMenu the same); the see-through version is
    gone.
  - Fade in: @keyframes gmIn is a 0.15 s fade in place; Sort By / Group Content's menu is drawn
    in .gm-subwrap, which fades in when it opens (gm-fadein) and not again while you move in it.
  - Fade out: gamemenu.js close() and SideMenu.close() fade out in 0.15 s (class "closing",
    @keyframes gmOut), then empty the panel; no buttons are taken meanwhile; one opened again
    during the fade is shown at once (GameMenu.open, SideMenu.open and GameInfoPanel.open
    stop it).
  - menufade.js (new) fadeOut(el, finish): the fade is ended at once when something else
    takes over meanwhile (anything the XMB hands its buttons to: xmb.overlay, other than the
    fading menu), checked before each frame is drawn: Information, a dialog, the next menu or
    a picker never show with the old menu still fading over them.
  - A Sort By / Group Content choice that closes the menu: it fades out as it was, its mini
    menu included, and the XMB stays moved left (body.gm-sub) until the fade ends, then slides
    back (gamemenu.js _subEnter hands the choice on first). Going back from Sort By / Group
    Content: their menu goes at once, as in v1.1.0 (no fade: it overlapped the panel moving
    back).
- xmb.js: a setting's name too long for the room before its value scrolls (marquee) while it's
  chosen, stopping short of the value.
- Intro: any controller button newly pressed skips it, as a key or a click does (intro.js
  offers its skip as window.__introSkip while it plays; main.js readGamepad() calls it, for
  the webview's Gamepad API and the native PlayStation controller reading). A button held
  from before the intro doesn't skip it, and the press doesn't reach the menu.
- Friends: no 99 limit (xmb-shared.js FRIEND_MAX = Infinity; the field is labelled "Number").
- Change Keybinds: choosing a new key for Close System (or putting F4 back) no longer closes
  the system. xmb-settings.js _syncHotkeys(quitOn): while the menu is open, changes are saved
  with the Close System key off, back on as it closes; main.js ignores the page's Close System
  while the menu is open and for a held key; quitkey.rs: a changed key only counts again once
  it's been seen up.

6. Closing games and emulators with Alt+F4
------------------------------------------------------------------------

Closing a game or an emulator with Alt+F4 (or F4, the Close System key) closed the system too:
the app came back to the front with the key still held.

- quitkey.rs:
  - KeyWatch, every 10 ms, for F4 and the Close System key: a new press, and whether the press
    a key is held by started with another program in front.
  - A press from elsewhere still counts as such for 1.5 s after it's let go (GRACE_MS); let go
    while the other program is still in front, the 1.5 s count from when the app is back in
    front (the app, busy coming back from the game, can take the close it was asked for after
    the key is up).
  - A press first seen less than 0.5 s after the app came to the front (FRESH_MS) is taken as
    made in the program before it (PPSSPP closes the moment Alt+F4 goes down, so the app is in
    front before the press is first seen).
  - The Close System key closes the system only on a new press made with the app in front
    ("Close System key pressed: closing" in the log).
  - held_from_elsewhere(): any of the above; tests for each case.
- lib.rs: the window asked to close while held_from_elsewhere() is not closed (prevent_close);
  quit_app (the page's Close System) is ignored then; both logged, and a close that goes
  through is logged too ("the window was asked to close: closing").
- main.js: the page's Close System is also ignored for 0.4 s after the window comes back to
  the front.
- Unchanged: the X button, Turn Off System, and Alt+F4 or F4 pressed while the system is in
  front close it as before.

1. Original Wave Style (the PS3's own wave)
------------------------------------------------------------------------

New: src/js/ps3wave/ - a JavaScript/WebGL2 port of sagemono/moyou (MIT, (c) 2026 sagemono),
drawing the XMB wave from the console's own lines.qrc (firmware 4.93).

- formats.js: QRC container reader (QRCC deflate + QRCF tree), .mnu parameter files, DDS and
  TGA textures.
- rsx.js: RSX Cg binary (.vpo / .fpo) to GLSL ES 3.00 translator (container parsing,
  microcode decoding, GLSL emission), output identical to moyou-cli transpile with hwprec.
- params.js: the console's parameter schedule (month maps, time-of-day presets, fades), with
  MaXMB additions: per-key mods (Wave and Sparkles Personalization scales the console's
  values), screen-preset overlays (override/music_1 for the Music Player's Visualizer Wave)
  faded by the clock, and a month override for PS3 themes.
- sim.js: the rope / wave simulation (sim/wave.cpp), warmed from a straight rope
  (36000 + 3000 n steps) to the console's start state.
- particles.js: the sparkles, with round-toward-zero float arithmetic as on the console.
- renderer.js: the full frame - background (back_colours0-2), wave sheet (lines1),
  LinesController, the HDR glare chain (GlareSourcePre, Copy, mips, Gaussian, AccGlare),
  ToneApplyDisplay and particles. MaXMB additions: a custom background map for Background
  Color squares, the wave without its background (over a picture or video), wave and sparkle
  colors, and the background rendered on its own (for icon / menu colors).
- original.js: the Wave Style driver (same controls as linkev's wave in wave.js): Background
  Color, Month and Time Colors, colors, waves / sparkles on or off, wallpaper, Still Waves,
  FPS Cap, focus and in-game power saving, controller motion.
  - Graphics safety: shaders compiled in the background with a start deadline; falls back to
    linkev's wave on context loss, start timeout or under 10 fps (remembered per computer).
  - Drawn at most at 1080 lines (540 minimum) and stretched to the window; follows
    Display Settings > Resolution.
  - Idle when nothing of it shows (waves and sparkles off over a picture / theme background,
    or the screen covered: body classes mpfull, pv-open, video-open); woken at once by _kick.
  - Background color read back asynchronously (backgroundPixelsStart/Take) and cached; the
    cache key includes the screen-preset overlay state, so colors aren't reused after the
    Music Player's Visualizer Wave fades out.
- warm.worker.js: the rope warm-up runs in a Web Worker while the shaders compile.
- wavecache.js (new): Wave Cache - the warmed rope state (Float64, cur + vel, base64) saved per
  settings key (up to 8, most recently used kept), bit-identical to a fresh run.
- background.js: the console's month / time-of-day background on its own (64 x 36), used for
  linkev's wave with Month and Time Colors and for icon colors; pre-built 8 s after start and
  kept across Wave Style changes.
- monthbg.js (new): MaXMB's own measured model of that background (PCA, 20 components) for when
  lines.qrc isn't there, so linkev's wave still shows the console's month colors.
- custom_render_plugin.prx is no longer needed (rope start states are computed, not read from
  the .prx); only lines.qrc is.
- wave.js: drives either style (Original / linkev); icon auto color, menu tint and glow taken
  from the live background; colors refreshed after a screen-preset fade (600 ms, 1.5 s).
- Background Color squares refitted row by row to console captures for the Original style
  (ORIG_SQUARES).
- intro.js: the boot intro starts on black and the background / wave rise to the menu's color
  and stay there (both styles).
- "linkev's" renamed "linkev" everywhere in the UI.

2. Music Player: Visual Player (Canyon and Earth)
------------------------------------------------------------------------

New: the PS3's Music Player visualizers, reverse-engineered from soundvisualizer_plugin,
custom_render_plugin, qgl_canyon_app, qgl_gaia_app and qglbase (firmware 4.93, Ghidra).

- spectrum.js: the console's spectrum - 512 stereo samples at 48 kHz, Gaussian window, FFT
  scaled 1/512, 17-tap Gaussian smoothing, 256 log-spaced bands, 3*ln(512m+1)/ln(513).
  SpectrumTap reads the Music Player's <audio> through a 48 kHz Web Audio graph (two
  analysers) and undoes the element's volume, so the visualizer reacts the same at any volume
  (the console reads the music before its volume).
- canyon.js: Canyon on WebGL2 from canyon.qrc - presets and settings (.mnu), normal map, RSX
  programs via rsx.js; terrain commit physics as decompiled (valley shape, damped spring per
  column, 5 smoothing passes, normals), 128 x 128 quad ring, color LUT, fog, line effect;
  depth of field (canyon_blur_ammount, 5 x canyon_layer_blur_blur, 256 x 144 x 4 blur
  pyramid) and feedback (canyon_layer_blur.fpo). Preset groups and timings as in
  custom_render (Bir, Voyage, Volcano, Volvic, Blue), terrain reset and 2 s morph on a new song.
  - Blur pyramid steps set to [0.5, 1, 2, 4] texels (slice 0 averaged, not blurred), matched
    to the console's video capture.
- earth.js: Earth from earth.qrc - cube faces from 2 x 2 JPEG tiles per face (layout worked
  out from the tile seams), stars and sun disk, the 30 camera flights (qglbase camera path:
  cubic segments, time-weighted key slopes), sun direction, per-flight settings; atmosphere
  drawn per pixel with Sean O'Neil's scattering model (GPU Gems 2) using the console's
  wavelengths and sun intensity; tuning (EARTH_TUNE) matched to a console video capture.
  - Faces prepared with canvas transforms (no per-pixel loops, no getImageData read-back),
    uploaded straight from an OffscreenCanvas, one face per task; verified pixel-identical
    to the previous method on all 18 faces.
- Both visualizers draw at about 60 fps (12.5 ms minimum between frames) whatever the display
  refresh rate or V-Sync setting.
- ui.js (MusicPlayer):
  - Square cycles Visualizer Wave -> Canyon -> Earth -> Visualizer Wave; a missing .qrc is
    skipped with a note naming the file.
  - Visualizers Cache: Canyon and Earth created 1.5 s after the player opens and drawn once
    while hidden (prepare()), shared through promises (_canyonReady / _earthReady), so
    switching is immediate. Freed on close (WebGL contexts lost, canvases removed, archives
    dropped) unless Save Cache in System Directory is on.
  - The <audio> element is CORS-enabled from the start and routed through the Web Audio graph
    when the player opens, so the song is never reloaded when a visualizer starts.
  - The Web Audio context is suspended when the player closes and resumed when it opens.
  - Visualizer canvases use visibility (not display) so they keep their size while hidden.
- ps3.rs / lib.rs: the PS3's own files (lines.qrc, canyon.qrc, earth.qrc) read from
  resources/ps3 only (command ps3_file, KNOWN list); in debug builds also from
  src-tauri/resources/ps3 and src-tauri/ps3. src-tauri/resources/ps3/README.txt added;
  the folder's contents are git-ignored.

4. Games and launching

- gamesrc.rs:
  - Store launchers: Steam (app manifests .acf, steam://rungameid), Epic Games, GOG (game
    info play tasks), Amazon Games and Battle.net games started through their launcher;
    EA app / Ubisoft Connect from their own program. Games found earlier are upgraded on the

  - Steam folders: the Steam root, a library, steamapps or steamapps\common can be added;
    Steam's own .url shortcuts start through Steam with Steam's icon.
  - Source folder modes: By Folders / By Executables ("How the Games are separated"), stored
    per folder (sync_modes); new folder rule: a folder is one game when it has a real root
    program (or inner game folders / game files, or root programs plus an uninstaller), and
    a folder of games with a loose installer or tool is still read one game per subfolder.
  - PS3 games: a Windows .lnk written per game (write_lnk / write_ico / rpcs3_cmdline), the way
    RPCS3's Create Shortcut makes them (--no-gui, by Title ID or EBOOT.BIN, with the icon).
  - Names ending in "Game" kept; duplicates across two source folders listed once.
  - Tests added (Steam, launchers, separate apps, edge cases, end-to-end installer case).
- library.rs: loose shortcuts / programs in content/Games wrapped in a folder of their own
  (wrap_loose_shortcuts).
- launcher.rs:
  - LaunchPlan::Raw: an .lnk pointing at RPCS3 starts RPCS3 directly with its exact argument
    line (raw_arg), not through cmd start.
  - Every game / program is spawned with NORMAL_PRIORITY_CLASS (it no longer inherits the
    app's lowered priority).
- focus.rs:
  - Follow: the game is followed by its pid, its descendants, processes running from its
    folder and new foreground programs; programs already running at launch are ignored;
    180 s timeout when the game never shows.
  - In game, the app and its WebView2 processes drop to BELOW_NORMAL, and so do the app's own
    FFmpeg processes (preloads, conversions, stills); restored afterwards.
- focus.rs: game mode ends when the app's own window is in front for two checks in a row
  (after something else was, once the game has been seen), even if a launcher or part of
  the game is still running; the launchers' helper processes (GameOverlayUI, Steam's
  error reporter and service, Epic's web helper, GOG Galaxy's helper, EA's background
  service) are never taken for the game; what's followed, the end, and what was still
  running when the user came back by hand are written to the log.
- focus.rs: a program already running before the game (by its file, e.g. SynTPEnh.exe
  restarting when the screen mode changes) or one in C:\Windows is never taken for the
  game; every way back from a game goes through return_from_game, which also repairs the
  window once per game (un-minimized and shown; the webview hidden, shown and set to the
  window's size, at once and again a second later, so the page draws anew; the window's
  own full screen is left alone) and logs its state; game_mode_end does the same repair.
- xmb.js: the page logs when it shows the menus again after a game.
- lib.rs: WebView2 starts with CalculateNativeWinOcclusion off, so the page never stops
  drawing because Windows reports its window as covered (after a full screen game the
  report could stay stuck: an invisible window and a sleeping page). Losing the focus or
  being minimized still quiets the app.
- focus.rs: "back in the app (the game has ended)" when nothing of the game is left.
- focus.rs: when the game's window opens while the app still has the focus (a game
  started through its store's client), the game's window is given the focus (once per
  window); the app also lets any program take the foreground when a game starts.
- focus.rs / lib.rs: after a game the page must answer (game_mode_end) within 8 seconds;
  if it doesn't (it stopped running during the game), it's loaded again. Both are logged.
- focus.rs: bring_to_front takes the foreground from a thread of its own (the window's
  thread only un-minimizes the window and focuses the page), and force_foreground no
  longer joins the foreground program's input (AttachThreadInput): with a program that
  didn't answer (a closing Steam game) it froze the app's window thread, leaving the
  window black or see-through and the page deaf. The game's window is given the focus
  the first time it's found without it, whoever had it (logged with who had it); the
  page's reload logs whether the window's thread still answers.
- focus.rs / lib.rs: a page that doesn't answer after a game is no longer reloaded (that
  didn't bring it back: WebView2 itself had stopped) but made anew with its window: the
  window is closed (the app kept running meanwhile: RunEvent::ExitRequested is held
  back), what's left of the app's own WebView2 processes ended, and the window built
  again as at the start (build_main_window, shared with the start). The log notes how
  many WebView2 processes the app had when the game started and when the page stopped.
- focus.rs: while a game runs, the log notes when the app's WebView2 processes end (with
  the program in front at that moment), and when the page stopped, whether WebView2
  wrote crash reports (EBWebView\Crashpad\reports in the webview folder) since the game
  started.
- focus.rs: when the page's processes ended during the game, the window is made anew as
  soon as the game ends (no 8-second wait), and their exit codes are logged.
- focus.rs / lib.rs: once the game is running, the page (the webview) is hidden until
  the game ends, so it draws nothing while the game changes the screen's mode; the
  window is black behind it (background_color), and the graphics card is left to the
  game. The log tells the order and timing in which the page's processes ended, and
  which one was the main one.
- focus.rs: when the page's processes end during a game, the log also lists the programs
  started since the game was (not the game's own) and the ones that ended along with them.
- focus.rs: the game watch's decisions (back in the app, the game's window given the
  focus, the game seen, ended or never shown) moved into GameWatch / BackWatch /
  hand_off, apart from Windows, with tests of whole sessions (a Steam game from start to
  end, Alt+Tab back with the game still open, a slow game loading behind the app, a game
  that never shows, a local game starting the real one, a store link). The game's folder
  is matched the same way on every system (tests).
- focus.rs / lib.rs / xmb.js: a program from a custom section (launch_game with
  program: true) no longer has the app's page hidden while it runs.
- focus.rs / lib.rs / main.js: the page answers "game-exited" at once (page_alive), so a
  living page is never taken for a stopped one (a program from a custom section didn't
  answer before, and its window would have been made anew 8 seconds later).
- lib.rs / focus.rs: the window getting the focus during a game (Alt+Tab or a click back)
  shows its hidden page at once, which then ends game mode by itself. The page is hidden
  only once the game has taken the front from the app (hiding it while the app was in
  front, as a game started directly loaded, gave the window the focus, which was taken
  for the user coming back: game mode ended before the game began), and the focus shows
  only a page the watch hid. Test: a local game starting with the app still in front.
- focus.rs / xmb.js: only the game's own window counts: the user is "back in the app"
  only after the game itself was in front, and the page is hidden only once the game's
  window is in front. A launcher's window (Steam's "launching" box) closing hands the
  front back to the app while the game is still loading (on a slower PC for a long
  while), which ended game mode before the game began. The page no longer ends game mode
  on the window's focus alone (the backend shows the hidden page when the user is back,
  which ends it). Tests: a launcher's box closing; a slow PC's Steam game from start to
  end; the page side (headless).
- wave.js: Still Waves and the power level are kept and given to every wave renderer made
  later (another user's Wave Style, or the linkev wave taking over from an Original wave
  that failed); before, the waves moved again with Still Waves On. xmb.js: a new user's
  first sign-in applies the Power Save Settings too.
- xmb.js: programs from custom sections end game mode as soon as the user is back in the app
  (game_mode_end on focus), so the controller works on the first press.
- Game panel (Triangle): consistent icon growth / name shift whether a preview, background or
  hidden title is involved; game music plays even with Background Music off.
